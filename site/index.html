Raftra

A fault-tolerant key-value store.

We kill its leader every ten minutes. Your writes survive.

Three servers in Mumbai agree on every write using Raft, a consensus algorithm implemented here by hand in Go. Lose any one of them, leader included, and nothing that was acknowledged is lost. The bars next to the name are those three servers, live.

      Try it in thirty seconds

      Every command goes to the live cluster. Writes land on the leader wherever it is, and the CLI moves on to the next server if one is mid-crash. Run raftra-cli with no arguments for an interactive shell.

      Playground rules

      • Keys up to 128 bytes, values up to 1 KiB, 10,000 keys in total.
      • 5 writes a second per IP address, with bursts of up to 10.
      • Everything is wiped at the top of every hour.
      • It’s public. Don’t store anything you wouldn’t post on a wall.

      How a write survives

      Nothing counts as written until a majority of servers has it on disk. Lose any one machine, including the leader, and every acknowledged write is still there.

      1. Any server takes the request. Clients can talk to whichever node answers first.
      2. Followers point to the leader. They reply with a 307 redirect to the leader’s address.
      3. The leader writes it to its own log and syncs the disk before going further.
      4. The leader sends it to the followers over gRPC on the private network. Each one stores it and replies.
      5. A majority has it, so it’s committed. The leader applies it to the key-value map and answers 200. Followers apply it on the next heartbeat.

      What it guarantees

      • At most one leader per term, and votes survive restarts.
      • Every server applies the same writes in the same order, and only after a majority stored them.
      • Any single server can die and no acknowledged write is lost.
      • A server on the losing side of a network split can’t commit anything.
      • Logs that disagree are repaired from the leader’s copy.
      • Pre-vote stops a returning server from disrupting a healthy leader.
      • A new leader commits an empty entry at once, so earlier writes become visible without waiting for traffic.

      What it doesn’t do (yet)

      • Reads on followers can be stale. There’s no ReadIndex or lease read.
      • No snapshots, so the log grows until the hourly wipe.
      • Cluster membership is fixed at three nodes.
      • No batching: every write is its own disk sync, which is why durable throughput is low.
      • No TLS or auth between nodes. The Raft port is only reachable on the private network.

      Measured, including the slow parts

      Three nodes on one Apple M2 laptop (macOS, Go 1.26.4), 100 concurrent clients, 80% writes. Full logs are in benchmark_results.md.

      How it was built

      Eight phases from an empty folder to a tested cluster, then a public one.

      1. FoundationProtobuf and gRPC interfaces, the node skeleton and its event loop.
      2. Leader electionRandomized timeouts, terms and votes. Exactly one leader per term.
      3. Log replicationAppendEntries, majority commit and the HTTP gateway for clients.
      4. PersistenceTerm, vote and log in bbolt, so a crashed node rejoins without losing anything.
      5. Failure testingAn in-memory network that can cut links and split groups, plus eight fault scenarios.
      6. Deployment and CLIDocker Compose for three nodes and a CLI that follows leader redirects.
      7. Benchmarks and metricsA load generator, failover timing and Prometheus metrics.
      8. Docs and polishREADME, a demo walkthrough and a full test pass.
      9. Then it went publicAbuse limits, release binaries for six platforms, three AWS servers, the ten-minute kill timer and this page.

      Two bugs the public cluster found

      A restarted server kept knocking out a healthy leader

      When the kill timer’s victim came back, it had been alone long enough to start an election and raise its term. Its first message carried that higher term, and the working leader stepped down for nothing. Every kill caused a second, pointless election.

      Fix: pre-vote (Raft thesis §9.6). A server now asks whether it could win before raising its term, and peers that heard from a leader recently say no. In three real-process test runs, the leader was knocked out three times before the fix and zero times after. Rejoining now takes 0.2–0.6 s.

      Committed data was invisible after a failover

      Raft lets a new leader commit entries from earlier terms only indirectly (§5.4.2). Until somebody wrote something new, the last writes before the crash stayed unapplied on the survivors.

      Fix: a no-op entry. Each new leader appends an empty entry in its own term as soon as it wins (§8). Committing it commits everything before it, so the data is back within one heartbeat. Ignoring stale election-timer fires in the same change cut the average failover from 322 ms to 245 ms, and the worst case from 611 ms to 291 ms.
